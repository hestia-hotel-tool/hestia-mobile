## Overview

Hestia is a multi-tenant mobile app for hotel operations teams: room
attendants, supervisors, housekeeping managers, front office and engineering.
Each hotel is a tenant, and every row is scoped to its hotel by Postgres
Row-Level Security. What each user can see and do comes from their role
(see [Access control](#access-control-rbac)).

Changes appear on every device in real time. Assigning a room, starting a
clean or inspecting a room updates other users' screens without a refresh,
and notifies the people concerned with an in-app toast and a push
notification.

## Features

| Area | What it does |
| ------ | -------------- |
| **Home** | Shift overview, recent activity per room, quick resume of paused rooms |
| **Rooms** | All-rooms list grouped by floor, with filters and search. Room detail covers guests, reservations, notes, assignment, priority and flags. Status changes go through a server-enforced state machine |
| **Staff** | Team roster by department and shift. Per-person activity shows credits, time used, and overtime as a negative number |
| **Assignments** | Assign rooms to attendants per shift (AM / PM). Rooms left unfinished are carried over at the end of a shift |
| **Tickets** | Maintenance and service tickets with photos, room picker, priority and status |
| **Lost & Found** | Register items found in departure rooms with photos. Track them from *stored* to *returned* or *discarded* |
| **Chat** | Direct and group chats, plus general announcements |
| **Tasks & notifications** | Typed in-app notifications (Cleaning Started, Room Inspected, Room Paused, General Announcement, and others), toasts, and push notifications with a lock-screen picture |
| **AI assistant** | In-app assistant backed by a Supabase Edge Function |
| **i18n** | All UI strings are translated; `npm run i18n:check` enforces it |

## Tech stack

| Layer | Choice |
| ------- | -------- |
| App | [Expo](https://expo.dev) SDK 56, React Native 0.85, React 19.2, [React Compiler](https://react.dev/learn/react-compiler) |
| Language | TypeScript (strict) |
| Navigation | [Expo Router](https://docs.expo.dev/router/introduction/) (file-based, `app/`) |
| Styling | NativeWind (Tailwind) through `@/tw`, plus design tokens generated from `design-system.json` |
| State | [Zustand](https://zustand.docs.pmnd.rs) with `useShallow` selectors |
| Backend | [Supabase](https://supabase.com): Auth, Postgres with RLS, RPCs, Storage, Realtime, Edge Functions (Deno), `pg_cron` |
| Push | Expo Push Service → APNs / FCM, with an iOS Notification Service Extension |
| Native | Continuous Native Generation: `ios/` and `android/` are generated by `expo prebuild` and are not committed |

## Getting started

```bash
# 1. Clone and install
git clone https://github.com/mua-wallace/hestia.git
cd hestia
npm install

# 2. Configure the environment
cp .env.example .env.development
#    Fill in EXPO_PUBLIC_SUPABASE_URL and EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY.

# 3. Run
npm start                 # Metro bundler. Press i (iOS) or a (Android)
npm run ios               # or build and run the native app directly
```

### Environment variables

| Variable | Required | Description |
| ---------- | :--------: | ------------- |
| `EXPO_PUBLIC_SUPABASE_URL` | ✅ | Supabase project URL |
| `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | ✅ | Supabase publishable (anon) key. It is safe to ship because RLS enforces access |
| `SUPABASE_SERVICE_ROLE_KEY` | ➖ | **Local scripts only** (`seed:*`). Never prefix it with `EXPO_PUBLIC_`, and never put it in a production env file |
| `APP_ENV` | ➖ | `development` (default), `preview` or `production`. Selects the app variant |

Env files (`.env`, `.env.development`, `.env.production`) are gitignored.
See [`docs/guides/SUPABASE_SETUP.md`](docs/guides/SUPABASE_SETUP.md) for the
full backend setup.

## App variants

`app.config.ts` produces three side-by-side installable variants from `APP_ENV`:

| `APP_ENV` | App name | iOS bundle ID / Android package | URL scheme |
| ----------- | ---------- | --------------------------------- | ------------ |
| `production` | Hestia | `com.hestiahotels.app` | `hestia` |
| `preview` | Hestia Preview | `com.hestiahotels.app.preview` | `hestia-preview` |
| `development` | Hestia Development | `com.hestiahotels.app.dev` | `hestia-dev` |

On iOS, each variant also embeds a notification service extension,
`<bundle id>.NotificationService`. See [Push notifications](#push-notifications).

## Building and releasing

### Local (Xcode / Android Studio)

```bash
# Generate the native project for the variant you want
APP_ENV=production npx expo prebuild --platform ios --clean
open ios/*.xcworkspace
```

In Xcode, select the **Hestia** scheme and a device, then choose
**Product → Archive** and upload to TestFlight. Signing uses team
`S2DF75LLN6` (set via `ios.appleTeamId`), and the extension target inherits it.

> **CocoaPods crashes with `Unicode Normalization not appropriate for ASCII-8BIT`?**
> Your shell locale isn't UTF-8. Add `export LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8`
> to `~/.zshrc`, open a new terminal, and run `cd ios && pod install`.

Re-run `prebuild` whenever `app.config.ts`, a config plugin in `plugins/` or a
native dependency changes. Never edit `ios/` or `android/` by hand, because
the next prebuild discards those edits.

### Cloud (EAS)

```bash
npm run build:dev:ios                                   # development client
eas build --profile preview --platform all              # internal testers
eas build --profile production --platform ios           # store build
eas submit --profile production --platform ios
```

Profiles are defined in [`eas.json`](eas.json). Build numbers are managed
remotely (`appVersionSource: remote`).

## Backend (Supabase)

- **Schema changes go through migrations only.** Add a timestamped file to
  `supabase/migrations/` (`YYYYMMDDHHMMSS_description.sql`), apply it to the
  **development** project first, and commit it together with the client code
  that depends on it.
- **Security:**
  - Every table has RLS keyed on the user's hotel.
  - Privileged operations are `SECURITY DEFINER` RPCs with a pinned
    `search_path`. Internal helpers are `REVOKE`d from `anon` and
    `authenticated`.
- **Realtime:**
  - `rooms` and `room_assignments` are in the `supabase_realtime` publication.
  - Clients subscribe through `useLiveRoomChanges`, with unique channel names
    from `src/lib/realtimeChannel.ts`.
- **Scheduled jobs:** `pg_cron` runs `process_room_service_timers`, which
  handles promise times, shift-end carry-over and the new-day reset.
- **Edge Functions:**

  ```bash
  supabase functions deploy notify     # fan-out of in-app and push notifications
  supabase functions deploy assistant  # AI assistant
  ```

## Access control (RBAC)

Permissions have a single source, the RBAC spec parsed by
`scripts/rbac/parse-spec.py`. Both outputs are generated from it:

1. `src/domain/rbac/permissions.ts`, used by the client (`usePermissions`, `<Can>`).
2. A seed migration for the `role_permissions` table, which the database uses.

```bash
npm run rbac:generate   # after editing the spec
npm run rbac:check      # every route is gated (run in CI)
```

The UI hides what a role cannot do. The database refuses it either way.

## Room status workflow

Room status changes go through one RPC, `room_action(room_id, action, …)`,
which checks the change against the rules in `room_status_rules`:

- **Room attendants** follow the normal flow:
  *Dirty → In progress → Paused / Cleaned → Inspected*.
- **Supervisors and managers** can move a room to any state. They can also
  set and clear promise times, override a status with a reason, and send a
  room back with a reason.
- Every change is recorded and notifies the people concerned (for example
  *Cleaning Started* or *Room Inspected*).

The client mirror is `src/features/rooms/utils/roomStatusMachine.ts`. For a
walkthrough written for hotel staff, see the
**[Room Status Guide (PDF)](docs/guides/Hestia-Room-Status-Guide.pdf)**.

## Push notifications

1. The app registers an Expo push token per device and stores it in Supabase.
2. The `notify` Edge Function sends each notification through the Expo Push
   Service with `mutableContent: true`.
3. On iOS, **HestiaNotificationService**
   (`plugins/notification-service/`, added at prebuild by
   `plugins/withNotificationServiceExtension.js`) turns the push into a
   Communication Notification. It shows a picture on the lock screen: the
   sender's photo for chats and announcements, otherwise a coloured icon for
   the notification type.

**Credentials:**

| Platform | Requirement |
| ---------- | ------------- |
| iOS | An APNs key (`.p8`) uploaded to expo.dev → *Credentials* for each bundle ID |
| Android | A Firebase project (`google-services.json`) with the FCM V1 key uploaded to expo.dev |

Without these, Expo rejects the sends with `InvalidCredentials`. In-app toasts
still work.

## Quality gates

Run these before every commit. CI and reviewers expect them to pass:

```bash
npm run typecheck
npm run lint
npm run rbac:check
npm run i18n:check
npx expo export --platform ios && npx expo export --platform android   # bundles cleanly
```

Every UI change must be verified on **both iOS and Android**
(see *Cross-Platform Rule* in [`AGENT.md`](AGENT.md)).

## Contributing

1. Branch from `main`: `feat/<topic>`, `fix/<topic>` or `refactor/<topic>`.
2. Use [Conventional Commits](https://www.conventionalcommits.org):
   `feat(rooms): …`, `fix(notification): …`, `chore: …`.
3. Keep migrations, generated files (RBAC, icons, tokens) and the code that
   uses them in the same PR.
4. Open a pull request against `main` that includes a short description,
   screenshots for UI changes, and the platforms you tested on.
5. Read [`AGENT.md`](AGENT.md) before your first PR. It defines the structure,
   styling, state and backend rules that reviews check.

## Security

- **Never commit secrets.** `.env*` files and `credentials/` are gitignored.
  Only `.env.example` is tracked.
- **The service-role key bypasses RLS.** Keep it out of the app bundle, out of
  `EXPO_PUBLIC_*` variables and out of production env files.
- Report vulnerabilities privately to the maintainers. Do not open a public
  issue.
